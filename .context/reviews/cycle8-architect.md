## Findings

### C8-A1: Parser parity drift continues — PDF, XLSX, CSV web-side still diverge

**Confidence:** High
**Severity:** High

The structural problem identified in Cycle 7 persists: six cycles of behavioral parity fixes have not prevented new drift. After Cycle 7 fixed HTML, JSON, and OFX web-side parity, PDF, XLSX, and CSV web-side parsers were missed and continue to use `Math.abs()` where server-side uses `amount <= 0` skip.

**Root cause:** Two independent implementations of the same parsing logic (server in `packages/parser/src/`, web in `apps/web/src/lib/parser/`). Every fix must be applied twice, and the second application is frequently missed.

**Cross-cycle pattern:**
- Cycle 2: First identified server/web structural duplication
- Cycle 6: Fixed server-side JSON negative amounts, missed web-side
- Cycle 7: Fixed web-side JSON, HTML, OFX; missed PDF, XLSX, CSV
- Cycle 8: PDF, XLSX, CSV still diverge

**Fix:** The only lasting fix is structural unification. Options:
1. Extract shared parser logic into `packages/parser/` and import from web via browser-compatible build
2. Generate web-side parsers from server-side templates
3. Create a comprehensive parity test matrix that tests both implementations with identical inputs

### C8-A2: scripts/build-json.ts duplicates Zod schema definitions

**Confidence:** High
**Severity:** Low

**File:** `scripts/build-json.ts:18-82`

The script defines its own Zod schemas (`cardRuleSetSchema`, `rewardRuleSchema`, etc.) that duplicate the schemas in `packages/rules/src/schema.ts`. This means schema changes require updates in two places.

**Fix:** Import schemas from `@cherrypicker/rules` instead of redefining them.

---

### C8-A3: FALLBACK_CATEGORY_LABELS generation tied to build script

**Confidence:** Medium
**Severity:** Low

**File:** `scripts/build-json.ts:436-449`

The fallback labels module is generated by `build-json.ts`, which is primarily a card data validator/builder. Category label generation is a side effect. If categories.yaml changes but cards.yaml doesn't, running the script is still required to update the fallback.

**Fix:** Consider a separate script or make the web app load category labels dynamically from `categories.json` at runtime, eliminating the need for a generated TypeScript module.

## Cross-Cutting Themes

1. **Duplication regenerates:** Even after extracting shared utilities (`buildCategoryLabelMap`, `normalizeHTML`), new call sites continue to duplicate logic when the shared version is not discoverable.
2. **Comments as liability:** False parity comments in `pdf.ts` and `csv.ts` mislead code reviewers into approving divergent behavior.
3. **Test gaps at boundaries:** No automated test verifies that web-side and server-side parsers produce identical output for the same input file.
