## Findings

### DOC-01 — The README labels `bun run verify` as CI-equivalent, but CI runs an additional browser suite

- Severity: **Medium**
- Confidence: **High**
- Classification: **confirmed**
- Locations:
  - `README.md:139-155`
  - `package.json:13-29`
  - `.github/workflows/deploy.yml:38-45`

The local-development instructions say `# CI와 같은 전체 검증` immediately before `bun run verify`. The `verify` script does not run `test:e2e`; the deployment workflow installs Playwright and runs `bun run test:e2e` as a separate required step.

Concrete failure scenario: a contributor follows the documented CI-equivalent command, gets a green result, and opens a change that still fails the browser regression gate. This is particularly misleading for navigation, upload, persistence, and visual interaction changes, where the missing suite is the relevant evidence.

Rationale: the command itself is valid, but the claimed equivalence is false. Readers should not need to inspect workflow YAML to discover a second required gate.

Suggested fix: either change the comment to describe `verify` as the static/unit/build verification bundle and show `bun run test:e2e` as the additional CI browser gate, or add a `verify:ci` script that composes both and use the same command in the workflow. Mention that Playwright Chromium/system dependencies are required for the latter.

### DOC-02 — Catalog counts and issuer summaries do not distinguish browseable cards from optimizer-executable cards

- Severity: **Medium**
- Confidence: **High**
- Classification: **confirmed**
- Locations:
  - `README.md:19-35`
  - `README.md:56-90`
  - `packages/rules/data/cards/hyundai/README.md:3-29`
  - `packages/rules/data/cards/hyundai/zero-edition3-discount.yaml:22-40`
  - `packages/rules/data/cards/hyundai/zero-edition3-points.yaml:22-40`
  - `packages/rules/src/card-availability.ts:13-26`

The README presents card recommendation and the 683-card catalog in adjacent capability sections without explaining that catalog visibility and optimizer eligibility are different sets. Issuer summaries amplify the ambiguity: Hyundai's representative table and prose recommend the ZERO series and state its 0.8%/1.2% benefits, while both highlighted ZERO Edition3 YAML files mark their sole reward `unsupported` because the merchant scope is unverified. The optimizer explicitly requires at least one `supported` reward, so neither card can participate in optimization.

Concrete failure scenario: a reader chooses the project because the documentation highlights ZERO Edition3 as an executable no-performance option, imports a statement, and cannot obtain that card in a recommendation. Nothing in the README or issuer summary explains that the card is catalog-only; the distinction appears only in runtime detail UI and source fields.

Rationale: the benefit facts may be useful for browsing, but an unqualified representative-benefit table reads as product capability in a repository whose headline purpose is recommendation. A raw YAML count is not a supported-recommendation count.

Suggested fix:

1. Add a concise root-README disclosure that cards/rewards marked `unsupported` remain browseable but are excluded from optimizer scoring, and that the issuer counts are catalog counts.
2. Generate a support/optimization-eligibility column or badge in issuer indexes and mark unsupported-only representative cards as “catalog only / not currently calculated.”
3. Extend `docs:check` so representative rows are reconciled not just to card existence/counts but also to current `support.status`; alternatively remove hand-maintained representative claims from the generated contract.
